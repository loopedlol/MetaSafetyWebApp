# Safety Lens Browser Prototype

Safety Lens is a controlled internal-pilot browser prototype for a Korean-style workplace TBM and risk-assessment workflow. It is not production-ready, legally certified, or a substitute for qualified workplace-safety judgment. It includes a normal browser dashboard and a compact `600x600` glasses-preview mode.

Its “AI” is deterministic mock reference material that does not inspect image pixels. Offline support is device-local, and the audit chain is tamper-evident rather than tamper-proof. A minimal Meta Ray-Ban Display Web App adapter supports the documented display and D-pad keyboard-event path; it does not claim camera, microphone, native SDK, or Neural Band API access.

Pilot operators should read [configuration](docs/configuration.md), [operations and backup/retention](docs/pilot-operations.md), the [security review](docs/pilot-security-review.md), and [responsible reporting](SECURITY.md) before using any non-test data.

The project is intended for internship/demo use: start a TBM, mark worker attendance, review hazards, add manual hazards or near-miss records with photo evidence, run mock AI suggestions, save sessions locally, and open a printable Korean HTML report.

## Architecture At A Glance

- Frontend: strict TypeScript Vite entrypoint in `src/main.ts`, application orchestration in `src/workflows/`, and owned API/state/storage/domain/view/type modules under `src/`.
- Backend: TypeScript Express entrypoint in `server.ts`, composition in `server/app.ts`, and owned middleware/services/validation/repository modules under `server/`.
- Demo hazards: loaded from `public/hazards.json`.
- Users, TBM records, ownership, upload metadata, and audit events: stored in `data/safety-lens.sqlite`.
- Private uploaded photos: opaque files in `uploads/`, referenced through owned SQLite metadata.
- Offline drafts, queued mutations, cached user profile, and photo blobs: stored structurally in IndexedDB (`safety-lens-offline-v1`).
- Application shell and `hazards.json`: cached by the versioned service worker after the first successful online visit.
- Korean report: generated by `GET /api/sessions/:sessionId/report` as printable HTML.
- Browser glasses-preview adapter: opened with `http://localhost:5173/?mode=glasses`, includes clearly labeled memo/photo mocks, and shares the normal session/report pipeline.
- Meta Display Web App adapter: selected only by `?mode=glasses&adapter=meta-display`; maps documented D-pad key events to the same application actions and disables unsupported camera/voice capture.
- Localization: Korean is the default interface/report language; English can be selected from the browser UI and is persisted as a non-sensitive preference.

## Run Locally

Install dependencies:

```bash
npm install
```

Create a local `.env` file:

```text
REGISTRATION_KEY=change-me-local-dev-key
SESSION_SECRET=replace-with-a-random-secret-of-at-least-32-characters
AI_MODE=mock
AI_API_KEY=
```

Run frontend and backend together:

```bash
npm run dev:all
```

Open:

```text
http://localhost:5173
```

Ports:

- Frontend: `http://localhost:5173`
- Backend: `http://127.0.0.1:3001`

You can also run them separately:

```bash
npm run dev
npm run server
```

Build the frontend:

```bash
npm run build
```

## SQLite Migrations And Legacy Import

This repository requires Node.js 24 or newer and uses its built-in SQLite driver. Apply pending migrations with:

```bash
npm run db:migrate
```

The default database is `data/safety-lens.sqlite`. Override it for recovery or verification work without touching the active database:

```bash
DATABASE_PATH=/tmp/safety-lens.sqlite npm run db:migrate
```

Import the old `data/users.json`, `data/sessions.json`, and optional `data/uploads.json` files once with:

```bash
npm run db:import-json -- --default-owner-email supervisor@example.com
```

Before reading records, the importer copies available source JSON into a timestamped `data/legacy-backups/` directory. Each source type and source ID is recorded in `legacy_imports`, so rerunning the command skips already imported records rather than duplicating them. When the legacy data contains exactly one user, that user can be selected automatically for records that predate ownership; otherwise `--default-owner-email` is required.

For rollback or recovery:

1. Stop the backend.
2. Copy `data/safety-lens.sqlite`, plus its `-wal` and `-shm` files when present, to a recovery location.
3. Restore a known-good database copy, or create a new database with `DATABASE_PATH=... npm run db:migrate` and rerun the importer against a timestamped JSON backup.
4. Never edit an applied SQL migration. Add a new numbered migration for forward fixes.

## Tamper-Evident Audit Trail

Important user, session, hazard-review, corrective-action, sharing, and upload changes append an `audit_events` record. Each event includes its ID, entity/action, actor, server timestamp, sanitized metadata, previous hash, and current SHA-256 hash. Database triggers reject ordinary updates and deletes.

Verify the chain with:

```bash
npm run audit:verify
```

This is tamper-evident, not tamper-proof or legally certified. A privileged attacker who can replace the database and recompute the entire chain can defeat local verification. Keep independent backups if stronger evidence retention is required. Passwords, registration keys, cookies, tokens, and secrets are filtered from audit metadata.

## Demo Checklist

### Normal Dashboard Demo

1. Open `http://localhost:5173`.
2. Register or login with the local registration key.
3. Start TBM for `서울 강동 스마트타워 신축공사`.
4. Mark worker attendance and, separately, any TBM acknowledgment recorded by the supervisor.
5. Mark one hazard `Controlled — safe to proceed` after review.
6. Mark another hazard `Action Required` and enter its immediate control, owner, due time, work status, and verification state.
7. Click Log New Hazard.
8. Add a new hazard or near-miss with title, location, description, action, and optional photo.
9. Click Generate Mock Suggestion. The app privately uploads the selected image first, then submits only its owned upload ID.
10. Confirm the result is labeled simulated and states that image pixels were not interpreted; accept, edit, or reject it after human review.
11. Save the entry and complete the checklist.
12. On Summary, record whether results were shared, including method and recipients when shared.
13. Save Draft, then resolve the displayed blockers and click Finalize.
14. Open Saved Sessions.
15. Click Open Report.
16. Use the browser print dialog for save-to-PDF if needed.

### Glasses HUD Demo

1. Open `http://localhost:5173/?mode=glasses`.
2. Register or login if needed.
3. Press `Enter` or `ArrowRight` to activate the primary action.
4. Select the attendance counts. This does not record worker acknowledgment.
5. Press `M` to capture the mock voice memo.
6. Press `P` to capture mock glasses photo evidence.
7. Press `1` to mark a hazard Controlled.
8. Press `2` on another hazard to mark Action Required; corrective-action details remain open for explicit entry.
9. Continue through hazards with `ArrowRight`.
10. Save a draft on the Summary card. Finalization remains blocked until sharing and corrective-action requirements are explicitly recorded.
11. Exit glasses mode and open the saved Korean report from the normal dashboard.

This is the browser-preview test adapter. `M`, `P`, `1`, and `2` are preview-only keyboard shortcuts and are not presented as Meta hardware gestures.

## Meta Ray-Ban Display Web App Integration

The integration follows Meta's public [Web Apps starter repository](https://github.com/facebookincubator/meta-wearables-webapp) and its [repository implementation guide](https://github.com/facebookincubator/meta-wearables-webapp/blob/main/AGENTS.md). The fuller developer portal currently requires a Meta developer login. The native [iOS DAT](https://github.com/facebook/meta-wearables-dat-ios) and [Android DAT](https://github.com/facebook/meta-wearables-dat-android) camera paths are separate paired-mobile-app SDKs and are not dependencies of this Vite web application.

### Confirmed capability boundary

| Capability | Meta Display Web App adapter | Evidence / handling |
| --- | --- | --- |
| Display output | Confirmed | Standard HTML/CSS/JS in a `600x600` viewport with `mrbd-web-app-capable=yes`. |
| Gesture input | Confirmed only as D-pad key events | Captouch/EMG input is delivered by the runtime as `ArrowUp`, `ArrowDown`, `ArrowLeft`, `ArrowRight`, `Enter`, and `Escape`. Safety Lens consumes key events; it does not call or invent a Neural Band gesture API. |
| Camera/photo access | Not confirmed for Web Apps | Production adapter returns `unsupported`; no mock or `getUserMedia` fallback is used. Evidence can be added later through the authenticated normal-browser private upload flow. Native DAT camera APIs are a different architecture. |
| Voice input | Not confirmed for Web Apps | Production adapter returns `unsupported`; no fixed transcript or browser microphone fallback is used. |
| Connectivity | Confirmed as standard web networking | Same-origin HTTPS `fetch` and browser online/offline events. There is no documented glasses-disconnect API, so the UI reports network state, not a hardware-link claim. |
| Local/offline storage | Confirmed at the standard Web App level | Service worker and Web Storage are documented. Safety Lens also uses IndexedDB for its existing queue; persistence on physical glasses must be verified before pilot reliance. |

Everything outside that table is an assumption until verified against current official documentation and physical hardware. In particular, cookie sharing with a phone, an on-device text keyboard, camera/microphone permission prompts, and direct device-connection state are not assumed.

### Adapter boundary

`src/device/device-adapter.ts` owns runtime capabilities, key-event translation, connection state, and capture results (`captured`, `unsupported`, `permission_denied`, or `failed`). The shared application receives device-neutral actions such as focus, activate, back, controlled, action-required, memo, and evidence. Meta-specific selection never enters the domain model; both adapters call the existing draft, private upload, synchronization, human-review, and audit paths.

The Meta adapter exposes only D-pad focus/activation/back. A hazard choice remains provisional until the separate hazard-confirmation screen is activated. The preview adapter retains labeled keyboard and capture mocks for deterministic tests.

### Build and configure for a physical-device test

No deployment is performed by this repository or these instructions.

1. Configure the production environment as described in [docs/configuration.md](docs/configuration.md), including strong secrets, `NODE_ENV=production`, the approved origin, proxy/HTTPS settings, and pilot data paths.
2. Run `npm run check`, `npm run test:browser`, `npm run security:secrets`, and `npm run security:audit` before preparing a test host.
3. Run `npm run build`. Host the built UI and Express API under one approved, publicly reachable HTTPS origin; private uploads must remain behind the existing authenticated API and must not be exposed as static files.
4. Use the device URL `https://<approved-host>/?mode=glasses&adapter=meta-display`.
5. In the Meta AI mobile app, open **Devices → Display Glasses → App connections → Web apps → Add URL**, and enter that exact HTTPS URL. Menu wording can change; confirm it against the current starter documentation before the physical test.
6. Do not configure any cloud image destination. This adapter cannot capture images. If evidence is needed, use the normal authenticated browser flow with the pilot's explicit consent and authorization procedure.

There is a current end-to-end blocker: the existing login/registration screen requires text entry, while the public Web Apps starter documents D-pad input and does not confirm an on-device text-entry or cross-device cookie mechanism. Safety Lens does not bypass authentication or provision a session token in the URL. A physical test may therefore stop at authentication unless Meta officially supplies a supported text-entry path. Resolving that would require a separately reviewed authentication/pairing design.

### Physical-device diagnostics

Use this exact path on the approved HTTPS test origin:

```text
https://<approved-host>/?mode=glasses&adapter=meta-display&diagnostics=1
```

Diagnostics are absent unless all three parameters have those exact values. The screen is non-production and local-only: it does not initialize the TBM offline store, synchronize queued operations, load hazards or private records, or submit diagnostics. It makes one read-only `GET /api/auth/me` request and reports only `authenticated`, `unauthenticated`, `network error`, or `unexpected response`; it never renders the returned identity.

The screen records documented Arrow/Enter/Escape `keydown` and `keyup` events, viewport/DPR, sanitized browser information, document focus/visibility, browser network state, service-worker state, and a disposable IndexedDB write/delete probe. Press `Enter` while **Exit diagnostics** is focused, select that action, or press `Escape` to return to `?mode=glasses&adapter=meta-display`. Exiting diagnostics does not create or authenticate a session.

Unknown `adapter=` values fail closed and never fall back to the browser-preview mocks. Diagnostics do not claim physical hardware connectivity: **online** means only `navigator.onLine`. Camera and voice remain unsupported in this Web App adapter.

### Device test checklist

Automated tests verify:

- explicit runtime selection and the adapter capability contract;
- D-pad key mapping and rejection of preview-only `1`, `2`, `M`, and `P` keys in the production adapter;
- online/offline state changes and listener cleanup;
- unsupported Meta camera/voice results and preview capture failure handling;
- browser rendering with fixed Meta viewport metadata, D-pad activation, human-confirmation flow, and no mock-photo control.

Browser preview verifies:

- the full normal and `600x600` workflow, including provisional safety decisions and final confirmation;
- labeled fixed memo and inline photo mocks only in the preview adapter;
- offline draft retention, queued synchronization, conflict handling, private evidence, and reports.

Physical glasses must verify:

- **Viewport:** the diagnostics screen reports `600×600`, fits without document overflow, and remains readable in Korean and English.
- **D-pad events:** each Arrow key, `Enter`, and `Escape` appears with the correct `keydown`/`keyup` type; preview-only number and letter shortcuts do nothing.
- **Authentication:** `/api/auth/me` reports only the expected category, and determine whether an officially supported text-entry path exists.
- **Cookie persistence:** after a supported login, close and reopen the Web App and record whether the authenticated category persists. Do not copy cookies into diagnostics.
- **IndexedDB persistence:** confirm the disposable probe passes and cleans up; separately verify the normal workflow queue survives an approved reload test.
- **Service worker:** record supported, registered, and controlling states before and after one successful online normal-workflow load.
- **Offline reload:** after the shell is controlled, disconnect networking, reload, and confirm diagnostics distinguish browser-offline state without claiming hardware disconnection.
- **Reconnect and queued synchronization:** create an approved test draft outside diagnostics, go offline, queue it, reconnect, and confirm exactly-once synchronization through the normal workflow.
- **Unsupported capture:** confirm there is no camera or voice action in the Meta adapter. Permission testing is applicable only if Meta later documents a supported Web App capture API.

Chromium automation verifies the browser contract but does not prove compatibility with physical Meta glasses, their firmware, the Meta AI host, or their persistence behavior.

### Exact Offline-First Manual Test

1. Start online with both servers running (`npm run dev:all`), open `http://localhost:5173`, authenticate, and wait for the first page to finish loading so the service worker can cache the application shell.
2. In browser developer tools, set Network to **Offline** (or disconnect the network without stopping the local browser page).
3. Start a TBM, record attendance and acknowledgment separately, review hazards, add a manual hazard, and attach a JPEG, PNG, or WebP photo. Confirm the UI says **Recorded on this device only** or **Queued for synchronization**, never that server sharing or saving succeeded.
4. Refresh while still offline. Choose **Restore Draft** and confirm the TBM fields and photo count return. In Application > IndexedDB > `safety-lens-offline-v1`, confirm the photo remains as a Blob in `evidence`.
5. Set Network back to **Online**. The queue retries automatically; use **Retry sync** if a prior attempt is marked failed.
6. Wait for **Synchronized to server**, open Saved Sessions, and confirm exactly one server session and one copy of each photo. Refresh again and confirm no duplicate session, event, or upload was created.

The conflict policy is conservative: a mutation based on an older server revision is marked **Conflict requires review** and is not retried automatically. The supervisor must explicitly choose **Review and keep local changes** before the local version is submitted against the newer revision.

### Saved Session / Report Test

1. Complete or partially complete a TBM.
2. Click Save Draft, or Finalize when no blocking reasons remain.
3. Open Saved Sessions.
4. Click Open Report.
5. Confirm the Korean report separates attendance, supervisor-recorded and independently verified acknowledgment, controlled hazards, open and closed corrective actions, unchecked items, sharing evidence, near-miss records, photo evidence, and mock AI notes.

## Keyboard Controls

Normal checklist screen:

- `ArrowRight`: next hazard
- `ArrowLeft`: previous hazard
- `1`: mark Controlled — safe to proceed
- `2`: mark Action Required

Glasses HUD mode:

- `ArrowRight` or `Enter`: activate the primary preview action
- `ArrowLeft`: previous preview screen
- `1`: mark hazard Controlled
- `2`: mark hazard Action Required without implying closure
- `M`: capture mock voice memo
- `P`: capture mock photo evidence
- `Escape`: previous preview screen

Meta Display adapter (`?mode=glasses&adapter=meta-display`):

- `ArrowUp`, `ArrowDown`, `ArrowLeft`, `ArrowRight`: move focus (or change the currently focused select value)
- `Enter`: activate the focused control; on a select, advance focus
- `Escape`: previous screen
- no number-key, memo, photo, or undocumented gesture shortcuts

## Local Data And Storage

Backend local files:

- `data/safety-lens.sqlite`: normalized users, sites, sessions, participants, safety records, upload metadata, sharing events, and audit events.
- `data/legacy-backups/`: timestamped source-JSON backups created by the importer.
- `uploads/`: opaque JPEG, PNG, and WebP evidence files; never served as a public static directory.

Browser storage:

- IndexedDB `safety-lens-offline-v1`: active drafts, evidence Blobs, cached non-secret user display profiles, and typed sync operations.
- Every operation includes a client operation ID/idempotency key, entity/session ID, device-observed time, retry count, last error, and sync status.
- `localStorage` is not used for active data. A legacy `safety-lens-active-draft-v1` value is imported once into IndexedDB and then removed.
- Local evidence is retained after upload confirmation for offline recovery; it is never deleted before the server confirms storage.
- Passwords, registration keys, cookies, and login form values are not stored in IndexedDB.

## Backend API Summary

- `GET /healthz`: process liveness without record or dependency details.
- `GET /readyz`: database-backed readiness; returns unavailable during shutdown.
- `POST /api/auth/register`: create a local user when `REGISTRATION_KEY` matches.
- `POST /api/auth/login`: login with email and password.
- `POST /api/auth/logout`: clear the local auth cookie.
- `GET /api/auth/me`: return the logged-in user.
- `DELETE /api/account`: password-confirmed account deactivation and identity pseudonymization; retained safety records follow the unresolved pilot policy.
- `POST /api/sessions`: validate and save a TBM session.
- Offline mutations send `Idempotency-Key`, `operationType`, and `baseRevision`; repeated keys replay the original response, and stale revisions return `409 Conflict`.
- `GET /api/sessions`: list saved sessions.
- `GET /api/sessions/:sessionId`: return one saved session.
- `GET /api/sessions/:sessionId/report`: return printable Korean HTML report.
- `POST /api/uploads`: upload JPEG, PNG, or WebP evidence photos up to 5MB each.
- `GET /api/uploads/:uploadId`: return owned evidence after authentication and integrity checks.
- `POST /api/ai/analyze-hazard`: validate an owned private `uploadId` and create a persisted provider analysis. Mock mode returns a deterministic simulated fixture and explicitly states that pixels were not interpreted.
- `PATCH /api/ai/analyses/:analysisId/review`: record an accepted, human-edited, or rejected decision with server reviewer and timestamp.

## Mock AI And Glasses Behavior

- Mock AI is deterministic backend fixture logic. It does not interpret image pixels and is not hazard detection.
- Evidence is privately uploaded and integrity-checked before suggestion generation.
- Mock suggestions require a separately persisted human accept/edit/reject decision and cannot change hazard or work-safety status directly.
- Browser-preview voice memo is a fixed prototype transcript, not speech-to-text.
- Browser-preview photo evidence is an inline mock image unless photo evidence is uploaded through the normal dashboard.
- The Meta Display Web App adapter supports only documented display and D-pad-delivered key input. Camera, voice, raw Neural Band, sensor, and GPS APIs are not implemented or simulated.

## Korean Report

Saved sessions can be opened as Korean printable HTML reports. The report includes:

- TBM/site/work/supervisor metadata.
- Worker attendance.
- Supervisor-recorded TBM acknowledgment, explicitly distinguished from worker verification.
- Independently verified acknowledgment evidence, when present.
- All hazards.
- Controlled hazards reviewed as safe to proceed.
- Open corrective actions.
- Closed corrective actions with explicit verifier evidence.
- Unchecked hazards.
- Near-miss records.
- Photo evidence thumbnails.
- Worker-sharing method, recipients, server-recorded time, and optional acknowledgment results.
- Mock AI notes labeled as human-reviewed reference information.

Use the browser print dialog for print/save-to-PDF. The app does not include a dedicated PDF generator yet.

## Known Prototype Limits

- This is a prototype, not a certified safety system.
- Mock AI is not real hazard detection and should not be treated as official safety judgment.
- Browser-preview photo evidence is mock evidence unless using the normal upload flow; the Meta adapter exposes no photo action.
- Physical Meta Display behavior, authentication, and IndexedDB persistence have not yet been verified on hardware.
- IndexedDB recovery and the sync queue are local to one browser profile/device; there is no background cloud relay when the browser is closed.
- Reports are HTML/print-to-PDF style, not generated PDF files.
- Authentication is local-file based and intended for demo use only.
- Sessions and evidence are owner-filtered with SQLite foreign keys, but this remains a single-machine prototype without remote replication or independent audit anchoring.
- Login and registration throttling is process-local and resets when the backend restarts.
- Saved data and uploads are local to this development machine.
